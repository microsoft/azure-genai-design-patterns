# Samples: Account Workbench declarative agent with three MCP plugins

These samples put the patterns from the [asset README](../README.md) and the [architecture guide](../docs/architecture.md) into a working package. **Account Workbench** is a declarative agent that combines three remote MCP servers, a pricing specialist worker agent, and one agent skill. Each server uses a different authentication path:

| Namespace | MCP server | Auth path | Tool discovery | Plugin manifest |
|---|---|---|---|---|
| `servicecrm` | `https://crm-mcp.contoso.com/mcp` | A1: OAuth 2.0 authorization code with PKCE, static registration | Pinned `functions[]` | [`ai-plugin-oauth.json`](ai-plugin-oauth.json) |
| `serviceknowledge` | `https://knowledge-mcp.contoso.com/mcp` | A3: Microsoft Entra SSO with on-behalf-of | Dynamic (`tools/list`) | [`ai-plugin-entra-sso.json`](ai-plugin-entra-sso.json) |
| `servicecatalog` | `https://catalog-mcp-dev.contoso.com/mcp` | C: anonymous (`None`), dev only, read-only | Dynamic (`tools/list`) | [`ai-plugin-anonymous.json`](ai-plugin-anonymous.json) |

All host names, IDs, and tenants are fictitious placeholders. Replace each `${{...}}` token with your own values before you package the agent.

## File list

| File | What it shows |
|---|---|
| [`manifest.json`](manifest.json) | App manifest (schema 1.29). Includes `copilotAgents.declarativeAgents`, `webApplicationInfo` for Entra SSO, and `validDomains` for all three MCP hosts. |
| [`declarativeAgent.json`](declarativeAgent.json) | Declarative agent manifest (schema v1.8). Includes character-budgeted instructions, `conversation_starters`, `capabilities`, three `actions`, `worker_agents`, and `agent_skills`. |
| [`ai-plugin-oauth.json`](ai-plugin-oauth.json) | Plugin manifest v2.4, `RemoteMCPServer` runtime. Uses `OAuthPluginVault`, pinned functions, and `states.reasoning` and `states.responding` instructions. |
| [`ai-plugin-entra-sso.json`](ai-plugin-entra-sso.json) | Plugin manifest v2.4 for the knowledge server. Uses the Entra SSO vault reference and dynamic discovery. |
| [`ai-plugin-anonymous.json`](ai-plugin-anonymous.json) | Plugin manifest v2.4 with auth type `None`. For the inner dev and test loop only. |
| [`mcp-tools-catalog.json`](mcp-tools-catalog.json) | Pinned tool catalog for the CRM server. Every schema is flat JSON Schema that M365 Copilot accepts. Each tool declares `readOnlyHint` or `destructiveHint`, and `_meta.ui.resourceUri` binds one tool to a widget. |
| [`sample-skill.md`](sample-skill.md) | Portable `SKILL.md` package with YAML frontmatter and progressive-disclosure steps for the account review workflow. |
| [`reference_mcp_server.py`](reference_mcp_server.py) | Reference implementation of the CRM server, standard library only. Covers Streamable HTTP, bearer validation, the server-side action gate, a `ui://` widget, and an offline self-test. |

## 1. Lay out the app package

The Microsoft 365 Agents Toolkit (`atk`) expects an `appPackage/` folder. Copy the samples into this layout:

```text
appPackage/
  manifest.json
  declarativeAgent.json
  ai-plugin-oauth.json
  ai-plugin-entra-sso.json
  ai-plugin-anonymous.json
  color.png                      192 x 192, full color
  outline.png                    32 x 32, white on transparent
  skills/
    account-review/
      SKILL.md                   copy of sample-skill.md
```

- **Icons.** Both icon files are referenced from `manifest.json` but not included here. Add your own, at exactly these sizes.
- **Skill folder.** `declarativeAgent.json` points `agent_skills` at `skills/account-review`, so the folder name must match.
- **Placeholders.** The toolkit replaces `${{NAME}}` tokens with environment variables of the same name. Keep values in your toolkit environment files or your pipeline's secret store, not in source control. Never commit a real tenant ID, client ID, or vault reference ID.

| Placeholder | Where it comes from |
|---|---|
| `TEAMS_APP_ID` | Generated by `atk provision`, or any new GUID for manual sideloading. |
| `AAD_APP_CLIENT_ID` | Application (client) ID of the Entra app that exposes the knowledge MCP API. |
| `CRM_OAUTH_REFERENCE_ID` | OAuth client registration in the Developer Portal (step 2a). |
| `KNOWLEDGE_SSO_REFERENCE_ID` | Entra SSO registration in the Developer Portal (step 2b). |
| `PRICING_SPECIALIST_AGENT_ID` | Title ID of the published pricing specialist agent used in `worker_agents`. |

## 2. Register authentication in the Developer Portal

Every vault reference ID ties a plugin to one auth registration. The rules are in [Developer Portal vault registration rules](../docs/authentication-paths.md#9-developer-portal-vault-registration-rules).

**2a. CRM server, Path A1 (OAuth authorization code with PKCE).**

1. In the Developer Portal, open **Tools > OAuth client registration** and select **Register client**.
2. Set the base URL to `https://crm-mcp.contoso.com`. Tokens are sent only to URLs under this base URL.
3. Enter the client ID, the authorization endpoint, the token endpoint, and the scopes `crm.read crm.write offline_access`. Turn PKCE on. Add a client secret only if your authorization server requires one for this client type.
4. Register `https://teams.microsoft.com/api/platform/v1.0/oAuthRedirect` as a redirect URI in your authorization server.
5. Copy the registration ID into `CRM_OAUTH_REFERENCE_ID`.

Full walkthrough: [Path A1 Developer Portal registration](../docs/authentication-paths.md#32-developer-portal-registration).

**2b. Knowledge server, Path A3 (Entra SSO with on-behalf-of).**

1. In Entra, expose the API as `api://knowledge-mcp.contoso.com/<client-id>` and add the `access_as_user` scope.
2. Pre-authorize the Microsoft 365 Copilot client application IDs listed in the guide.
3. In the Developer Portal, open **Tools > Microsoft Entra SSO client ID registration**. Register the client ID with base URL `https://knowledge-mcp.contoso.com`, then copy the registration ID into `KNOWLEDGE_SSO_REFERENCE_ID`.
4. Make sure `webApplicationInfo.resource` in `manifest.json` matches the Application ID URI exactly.

Full walkthrough: [Entra app registration for the MCP API](../docs/authentication-paths.md#52-entra-app-registration-for-the-mcp-api).

**2c. Catalog server, Path C (anonymous).** No registration is needed. Remove `ai-plugin-anonymous.json` and its `servicecatalog` action before you publish beyond a dev tenant. See [Path C](../docs/authentication-paths.md#7-path-c-anonymous-none).

## 3. Validate, provision, and sideload

```bash
atk validate --package-file ./appPackage/build/appPackage.dev.zip   # schema and rule checks
atk package --env dev                                               # builds the zip
atk provision --env dev                                             # registers the app, fills TEAMS_APP_ID
atk preview --env dev --m365-host copilot                           # opens Copilot with the agent sideloaded
```

Flags vary by toolkit version. Run `atk <command> --help` to check them. If validation fails, follow [Stage 1: package validation](../docs/troubleshooting-and-diagnostics.md#2-stage-1-package-validation). Before you ship, lint the tool schemas with [lint before you ship](../docs/troubleshooting-and-diagnostics.md#43-lint-before-you-ship).

## 4. Run the reference MCP server

The server needs Python 3.9 or later and has no third-party dependencies. Run it from the repository root.

**Offline self-test.** This is the default mode. It runs 52 checks in about a second and exits with code 0 when they all pass:

```bash
python assets/m365-and-copilot/m365-mcp-plugin-integration/samples/reference_mcp_server.py
```

The checks cover:

- Protocol negotiation and session handling.
- Each token rejection reason.
- Schema validation of tool arguments.
- The `R` and `W1` to `W4` gate. These are tests T5 to T10 of the [confirmation card test protocol](../docs/troubleshooting-and-diagnostics.md#8-confirmation-card-test-protocol).
- The 20 KB result cap.
- The `ui://` resource.
- A loopback HTTP smoke test.

**Serve locally.**

```bash
python assets/m365-and-copilot/m365-mcp-plugin-integration/samples/reference_mcp_server.py --serve --port 8080
```

At startup the server prints the endpoint `http://127.0.0.1:8080/mcp` and a dev bearer token. The token is valid for one hour and only for this process, because the signing key is regenerated on every run. Each request writes one JSON log line to stderr. The line includes `correlation_id`, `mcp_session_id`, the tool name, the gate decision, the status, and the latency.

Example session with `curl`. Set `TOKEN` to the printed token first. On Windows PowerShell, use `curl.exe` and put the JSON body in a file (`--data @body.json`).

```bash
H='-H Content-Type:application/json -H Accept:application/json,text/event-stream -H MCP-Protocol-Version:2025-06-18'

# 1. initialize: the response headers include Mcp-Session-Id
curl -i $H -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/mcp \
  --data '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}'

# 2. tools/list and tools/call: send the session ID returned by step 1
curl $H -H "Authorization: Bearer $TOKEN" -H "Mcp-Session-Id: $SESSION" http://127.0.0.1:8080/mcp \
  --data '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'
curl $H -H "Authorization: Bearer $TOKEN" -H "Mcp-Session-Id: $SESSION" http://127.0.0.1:8080/mcp \
  --data '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"get_account_summary","arguments":{"account_id":"ACC-1001"}}}'

# 3. Protected resource metadata (RFC 9728): no token needed
curl http://127.0.0.1:8080/.well-known/oauth-protected-resource
```

**Anonymous mode.** `--serve --allow-anonymous` accepts requests without a token and exposes only the `R` tools (`get_account_summary` and `search_opportunities`). It simulates Path C for inner-loop testing. Never deploy it.

### Status and refusal codes

Token problems return HTTP 401, or 403 for a missing scope. The response carries a `WWW-Authenticate` header that points at the resource metadata URL. Gate refusals return a normal tool result with `isError: true` and a user-safe message, so the orchestrator can explain the refusal instead of retrying.

| Code | Kind | Meaning |
|---|---|---|
| `missing` | Auth (401) | No `Authorization: Bearer` header. |
| `expired` | Auth (401) | `exp` is at or before the current time. The sample applies no clock-skew allowance; production validators usually allow a few minutes. |
| `bad_signature` | Auth (401) | The token is malformed or its signature does not verify. |
| `bad_aud` | Auth (401) | `aud` is not `https://crm-mcp.contoso.com`. |
| `bad_iss` | Auth (401) | `iss` is not the expected authorization server. |
| `bad_tid` | Auth (401) | The tenant is not on the allowlist. |
| `scope` | Auth (403) | `insufficient_scope`: for example, a write tool called with only `crm.read`. |
| `invalid_arguments` | Tool error | Arguments fail the tool's input schema. |
| `writes_disabled` | Gate | An administrator has paused write tools. |
| `daily_cap_exceeded` | Gate | The per-user daily write cap (20) is reached. |
| `draft_required` | Gate | `submit_order` was called without a draft that the same user created. |
| `draft_already_used` | Gate | The draft was already submitted. |
| `approval_required` | Gate | `notify_account_team` was called without a valid approval token. |
| `result_too_large` | Tool error | The serialized result exceeds 20 KB. |

Successful `W1` to `W4` calls return a `receipt_id` (`RCP-...`) that the agent quotes back to the user. To map these codes to the failing stage, see [Stage 5: token acquisition and validation](../docs/troubleshooting-and-diagnostics.md#71-stage-5-token-acquisition-and-validation).

## 5. Reach the local server from Microsoft 365 Copilot

M365 Copilot calls MCP servers from the cloud, so it cannot reach `127.0.0.1`. For an end-to-end test:

- Put the local server behind an HTTPS reverse proxy or a tunnel that your organization approves, with a valid TLS certificate.
- Add that host name to `validDomains` in `manifest.json`.
- Point the plugin's `runtimes[].spec.url` at the new host.
- Keep the tunnel private, and shut it down when you finish testing.

For the widget, follow the [MCP Apps testing checklist](../docs/mcp-apps-and-interactive-widgets.md#8-testing-checklist).

## 6. Before production

The reference server is teaching code. Before it handles real data:

- Replace the HS256 dev signature check with RS256 validation against the issuer's signing keys (JWKS), and cache the keys with rollover.
- Remove dev token minting and anonymous mode from the build entirely.
- Move sessions, drafts, daily caps, and audit rows into durable storage that is shared across instances.
- Load signing and approval keys from a managed secret store, and use managed identity to reach it.
- Restrict allowed `Origin` values to known hosts, and serve only over TLS.
- Add per-user and per-tenant rate limiting that returns `429` with `Retry-After`.
- Send the structured logs to your telemetry backend, and correlate them with the `correlation_id`.
